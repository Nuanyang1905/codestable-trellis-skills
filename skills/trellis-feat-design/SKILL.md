# Feat Design — 写代码之前，先把要做什么想清楚

在 brainstorm（PRD）和 implement（写代码）之间插入设计阶段。AI 产出一份**人能看懂的设计文档**，用户确认无误后，AI 才按设计写代码。写完之后对照设计逐条验收。

**核心原则**：设计文档是写给人看的，不是写给 AI 的。读者打开后 5 分钟内要能抓到全部要点。

---

## 启动检查（每次先做）

### 1. 确认前置输入完整

PRD 至少能回答这四个问题，缺了先补：
- **用户目标**：谁、要完成什么事
- **核心行为**：主要做什么（用大白话）
- **成功标准**：怎么算做对了（可观察的行为）
- **明确不做**：什么这次不碰

说不清 → 退回 brainstorm，不要硬写。

### 2. 确认产出位置

- 设计文档写入当前 task 目录：`.trellis/tasks/{task}/design.md`
- 验收清单写入同目录：`.trellis/tasks/{task}/checklist.yaml`

### 3. 判断用户角色（决定设计文档的语言）

开口问一句（如果不知道的话）：
> "你对这个项目的代码熟悉吗？设计文档里可以用技术术语，还是用大白话描述？"

- 用户说"不懂代码"/"不会编程"/"用大白话" → **非技术角色模式**
- 用户说"用技术术语"/"我能看代码" → 技术角色模式

---

## 非技术角色模式（硬约束）

用户看不懂代码时，设计文档**必须用行为语言**，遵循以下规则：

### 禁止出现的词
函数名、类名、API 路径、库名、框架名、文件路径、数据库表名、技术协议名

### 应该出现的词
页面名称、按钮文字、输入框标签、提示信息、操作步骤、用户能看到/听到的变化

### 格式："现状 → 变化"两段式，用行为描述

```markdown
## 现状（现在是怎么做的）
用户打开设置页面 → 看到「修改密码」按钮 → 点进去输入旧密码+新密码 → 提交后看到「修改成功」

## 变化（这次要改成什么样）
用户在设置页面 → 多了一个「账号安全」入口 → 点进去能看到登录记录、可一键踢掉陌生设备
```

### 成功标准写成可观察行为

✅ "点「登录」→ 看到首页 → 右上角显示用户名"
❌ "AuthService.login 返回 200 并设置 session cookie"

### 挂载点写成用户能感知的影响

✅ "会影响：登录页、注册页、个人设置页、管理员用户列表"
❌ "改动范围：src/auth/Login.tsx, src/auth/Register.tsx"

---

## 技术角色模式

可以使用技术术语，但设计文档仍然聚焦在**编排层**（架构、接口、流程），不写实现细节。

### 设计写什么
- 名词层：实体、数据结构、接口签名（现状→变化）
- 编排层：主流程、模块交互（开头一张图建心理模型）
- 流程级约束：错误语义、幂等性、并发、扩展点
- 挂载点清单：删了它 feature 就消失的地方

### 设计不写什么
- 改动文件清单、函数级落点、测试代码、库选型细节
- 这些归 implement 阶段决定

---

## 设计文档模板

以下模板适用于非技术角色。技术角色把行为描述替换为技术描述即可。

```markdown
# {功能名称} 设计方案

> 设计日期：YYYY-MM-DD | 状态：draft | 关联 PRD：prd.md

## 0. 术语约定
（如有容易混淆的词，在这里说清楚）
- 「XX」指的是：YY
- 「AA」和「BB」的区别是：CC

## 1. 决策与约束

### 需求摘要（一句话）
{谁} 在 {什么场景} 下，能 {做什么事}

### 关键决策
- 决策 1：{什么决定 + 为什么这样选}
- 决策 2：{同上}

### 明确不做
- 不做 X（原因：{一句话}）
- 不做 Y（原因：{一句话}）

## 2. 现状与变化

### 2.1 现状（现在是怎么做的）
{行为描述。如果这是全新功能，写"当前系统没有此功能"}

### 2.2 变化（这次要改成什么样）
{行为描述。用「用户打开 X → 看到 Y → 可以做 Z」的格式}

### 2.3 挂载点（改了之后哪些地方会被影响）
- 挂载点 1：{页面/功能名} — 影响：{什么变化}
- 挂载点 2：{同上}
（一般 3-5 条，超过说明耦合太散，要警惕）

### 2.4 推进顺序
- 第 1 步：{从用户能感知的最小变化开始}
- 第 2 步：{接着做什么}
- 第 3 步：{最后收尾什么}

## 3. 验收契约

### 正常场景
- [ ] S1：{输入/触发 → 期望可观察结果}
- [ ] S2：{同上}

### 边界与错误场景
- [ ] E1：网络断了 → {用户看到什么}
- [ ] E2：数据为空 → {用户看到什么}
- [ ] E3：操作冲突 → {用户看到什么}

### 反向核对（确保没多做）
- [ ] 未实现 {明确不做的事项 X}
- [ ] 未改动 {明确不碰的范围 Y}

## 4. 与项目架构文档的关系
（实现完成后，trellis-check 会按此节把稳定内容归并到 `.trellis/spec/`）
- 新增/变化的实体、类型、接口：{描述，无则写"无"}
- 新增/变化的跨模块流程或编排：{描述，无则写"无"}
- 新增的流程级约束（幂等/并发/错误语义等）：{描述，无则写"无"}
```

---

## 起草纪律

### 1. 碰到没说清的地方，停下来问
不许自己猜一个填上去。方式：
- 声明假设："这部分你还没说，我假设是 A，对吗？"
- 给选项："这里有两种做法：A（好处/代价）和 B（好处/代价），你倾向哪个？"

### 2. 整稿一次性给用户 review
不要写一节发一节。用户看完局部发现不了"第 1 节范围跟第 2 节变化对不上"这种跨节矛盾。

### 3. 不在设计阶段偷偷扩大范围
用户说加登录，就别在设计里顺便加注册。验收时对不上的东西最后都要返工。

## 流程步骤

### Step 1：读 PRD + 扫上下文
- 读 `prd.md` 全文
- 如果有 `research/` 目录，读相关文件
- 如果有 `design.md` 已存在：
  - `status: draft` → 跳到 Step 4（整体 review）
  - `status: approved` → 问用户"接着改还是重来"

#### 1.1 扫已有知识（防术语冲突 + 防重复发明）

动笔写设计前，先搞清楚系统里已经有什么：

**扫 spec（编码规范与架构）**：
```bash
ls .trellis/spec/
cat .trellis/spec/*/index.md 2>/dev/null
```
读与本次改动相关的 spec 文件，了解已有模块/接口/约束。如果 design 要引入新模块或跨模块接口，把发现写进 design 第 4 节。

**扫 compound（历史踩坑与好做法）**：
```bash
grep "<关键词>" .trellis/spec/guides/compound.md 2>/dev/null
```
搜索是否有同类功能的历史经验。命中相关记录时：
- 坑点 → 在 design 的"边界与错误场景"中引用，避免重蹈覆辙
- 好做法 → 在 design 的"关键决策"中引用，遵循已验证的模式

**术语 grep 防冲突**：
新概念名（页面名、功能名、实体名）在代码和已有 design 中 grep 一遍：
```bash
grep -r "<新术语>" .trellis/spec/ .trellis/tasks/ 2>/dev/null
# 再搜代码目录（根据项目实际结构调整路径）：
grep -r "<新术语>" src/ lib/ app/ 2>/dev/null
```
- 命中 → 在 design 第 0 节"术语约定"中明确区分新旧含义
- 未命中 → 通过，新术语无冲突

**搜同类 feature**：
```bash
ls .trellis/tasks/ | grep -v archive
```
有同类 feature 读过其 design.md → 参考其挂载点和边界处理，避免每次重新发明。

### Step 2：写初稿
按上面模板写完整设计文档，frontmatter 加 `status: draft`。

### Step 3：整体提交 review
把完整文档给用户，附一句：
> "这是完整设计方案，你看一下有没有跟你想的不一样的地方？特别是「明确不做」和「边界场景」这两块。"

用户提意见 → 改 → 再review，直到放行。

### Step 4：确认通过
用户确认后，`status` 改为 `approved`。

### Step 5：生成 checklist
从 design.md 第 3 节「验收契约」抽出 checklist.yaml：

```yaml
feature: "{task-name}"
status: approved
steps:
  - id: step-1
    description: "{推进顺序第 1 步}"
    status: pending
  - id: step-2
    description: "{推进顺序第 2 步}"
    status: pending
checks:
  - id: S1
    description: "{正常场景 S1}"
    status: pending
  - id: S2
    description: "{正常场景 S2}"
    status: pending
  - id: E1
    description: "{边界场景 E1}"
    status: pending
  - id: REV-1
    description: "反向核对：未实现 {明确不做 X}"
    status: pending
```

---

## 退出条件

- [ ] design.md frontmatter 带 `status: approved`
- [ ] 第 1 节含"明确不做"
- [ ] 第 2 节用"现状→变化"两段式
- [ ] 第 2.3 挂载点 3-5 条
- [ ] 第 3 节验收契约覆盖正常+边界+错误+反向核对
- [ ] checklist.yaml 已生成
- [ ] 用户终审确认

退出后告诉用户：
> "设计方案已确认。下一步告诉 AI '开始实现'，AI 会按照这份设计写代码。写完后我会对照 checklist 逐条验收。"

---

## 容易踩的坑
- PRD 没写清楚就开始设计 → 返工率高
- 没扫已有 spec/compound 就动笔 → 术语冲突、重复发明轮子
- 只写"变化"不写"现状" → 读者不知道改了什么
- 挂载点写成改动文件清单 → 那是实现细节，不是挂载点
- 分批发给用户 review → 用户看不出全局一致性
- 技术角色用模糊描述（"让它能跑"）→ 验收时对不上
- 非技术角色用技术术语 → 用户看不懂，失去把关作用
