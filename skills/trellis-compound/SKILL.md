# Compound — 知识沉淀

每次做 feature 或修 bug 都会留下 spec 和 design。但 spec 记录的是"怎么做"，design 记录的是"做成什么样"——**都不会记录"踩了什么坑"和"发现了什么更好的做法"**。没有沉淀的项目总在重复踩同一个坑。

两条轨道：

| 轨道 | 记录什么 | 示例 |
|------|---------|------|
| **坑点（pitfall）** | 调过的 bug / 绕过的配置陷阱 / 环境问题 / 集成失败 | "改了 A 文件的类型定义，B 文件的测试全部挂掉，因为 mock 数据没同步" |
| **好做法（knowledge）** | 最佳实践 / 工作流改进 / 可复用模式 | "表单验证应该在前端和后端各做一遍，只做一端会漏" |

两者都写入 `.trellis/spec/guides/compound.md`（追加模式，每条新记录一个 `###` 小节）。

---

## 什么时候触发

| 情境 | 说明 |
|------|------|
| trellis-check 验收完成 | 主动问"这次有没有踩坑或发现好做法？" |
| 修了一个非显而易见的 bug | 主动问"这个 bug 的根因要沉淀吗？" |
| 用户主动 | "记录一下"、"沉淀知识"、"把这个坑记下来"等 |
| 用户说"终于搞定了/原来是这样" | "听起来是个值得记下来的发现，要记吗？" |

主动推荐一句话即可，用户说"不用了"立刻跳过——重复推反而让人烦。

## 沉淀流程

### Step 1：识别来源

从对话上下文提取：
- **来源类型**：feature 工作流 / bug 修复 / 独立发现
- **关联产物**：task 路径（如有）
- **粗分轨道**：坑点 or 好做法。"修了什么坏了的东西" = 坑点；"发现了什么更好做法" = 好做法。两者都有就分两条

来源不明确问用户**一个问题**澄清，不要猜。

### Step 2：查重（必做）

在 `.trellis/spec/` 下搜索是否已有类似记录：
```bash
grep -r "<关键词>" .trellis/spec/guides/compound.md .trellis/spec/
```

发现重叠时：
- 内容需要补充 → **更新旧段落**，在末尾加 `> 更新于 YYYY-MM-DD：{新增内容}`
- 内容已被覆盖 → 不重复写，告诉用户"这条已记录在 {位置}"
- 内容冲突 → 列出来让用户裁决

### Step 3：提炼（一次一个问题）

**坑点轨道**问：
1. 你最初观察到的现象是什么？
2. 哪些解法试过但没用？（失败的尝试是后人最宝贵的信息）
3. 最终怎么发现真正原因的？
4. 下次可以更早发现吗？怎么发现？

**好做法轨道**问：
1. 这个模式在什么情境下最有价值？
2. 不这样做会出什么问题？
3. 有没有不适用的反例？

用户对某问题说"没什么"或"跳过"就跳过——宁可少一节也不用空话填充。

### Step 4：起草 + 用户确认

一次性起草完整内容，一次性展示给用户确认。不分批。

### Step 5：落盘

写入 `.trellis/spec/guides/compound.md`：

**首次初始化**（文件不存在时）：
先创建文件，写入头部：
```markdown
# Compound — 知识沉淀

> 双轨记录：坑点（pitfall）与好做法（knowledge）。每次踩坑或发现更优做法时追加。

---

```

**追加模式**（文件已存在时）：
在文件末尾追加新记录：

```markdown
### {日期} - {坑点/好做法} - {一句话标题}

**轨道**：坑点 / 好做法
**日期**：YYYY-MM-DD
**关联**：{相关 task/feature}

**现象/场景**：{描述}

**根因/原理**：{为什么}

**解法/做法**：{怎么做}

**下次怎么发现**：{预防措施}
```

**更新已有记录**（查重发现重叠，补充而非新建）：
在原记录的末尾追加一行：
```markdown
> 更新于 YYYY-MM-DD：{新增内容，如"补充了 XX 场景下的反例"}
```
同时在原记录的 frontmatter 区（或标题行）确认日期字段保持原始日期不变——`updated` 行自身记录了更新时间线。

### Step 6：可发现性检查

写完检查 `AGENTS.md` 或项目根目录下的 AI 指引文件有没有提到 compound 知识库。

如果**没有**，给出以下建议（不自作主张改文件）：

> 建议在 `AGENTS.md` 中加一行：
> ```
> - 踩坑经验和好做法记录在 `.trellis/spec/guides/compound.md`，写代码前 grep 相关关键词避免重蹈覆辙
> ```

如果 `AGENTS.md` 不存在，建议：
> 建议创建 `AGENTS.md`，至少包含：
> ```markdown
> - 编码规范：.trellis/spec/
> - 历史经验（坑点与好做法）：.trellis/spec/guides/compound.md
> ```

- [ ] 轨道分类正确（坑点 / 好做法）
- [ ] 已查重，无重复记录
- [ ] 所有模板节都填了（跳过的有明确原因）
- [ ] 已落盘到 compound.md
- [ ] 已做可发现性检查

## 与 trellis-update-spec 的区别

| 维度 | trellis-compound | trellis-update-spec |
|------|-----------------|---------------------|
| **记什么** | 踩坑经验、好做法 | 编码规范、接口契约 |
| **读者** | 人（防止重复踩坑） | AI（指导下次怎么写代码） |
| **落盘** | `compound.md` | `spec/<layer>/*.md` |
| **格式** | 叙事性：现象→根因→解法→预防 | 契约性：签名→矩阵→用例→测试点 |
| **触发词** | "记下来""沉淀""踩坑" | "更新 spec""补充规范" |

---

## 容易踩的坑
- 没查重就落盘 → 同一件事记了两遍，后人不知道该看哪个
- 只写现象不写根因 → 后人只知道"出过问题"但不知道怎么防
- 坑点不写"试过但没用的解法" → 后人会重复走你走过的死胡同
- 好做法不写"不适用的反例" → 后人把经验当铁律，在不该用的地方硬用
- 分批发给用户 review → 用户看不出全局一致性
